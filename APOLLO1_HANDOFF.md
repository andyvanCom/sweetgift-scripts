# SweetGift: передача проекта на Apollo1

Этот документ — стартовая точка для продолжения разработки SweetGift на
компьютере Apollo1. Актуальный источник кода и документации — ветка `main`:

```text
https://github.com/andyvanCom/sweetgift-scripts
```

Локальные пути с других компьютеров использовать нельзя. Работать следует из
папки, в которую репозиторий клонирован на Apollo1.

## 1. Первоначальная настройка

Проверить авторизацию GitHub CLI:

```bash
gh auth status
```

Если авторизации нет:

```bash
gh auth login
```

Клонировать проект и перейти в него:

```bash
git clone https://github.com/andyvanCom/sweetgift-scripts.git
cd sweetgift-scripts
git checkout main
git pull --ff-only origin main
```

Если папка уже существует:

```bash
git status --short
git fetch origin
git checkout main
git pull --ff-only origin main
```

Перед работой с базой подключить Supabase через MCP либо официальный CLI.
Проект SweetGift:

```text
Project ref: rvgvbxipccbkytmhltmi
```

Для CLI:

```bash
supabase login
supabase link --project-ref rvgvbxipccbkytmhltmi
```

Секреты, токены, пароли, SMTP-реквизиты и `service_role` нельзя записывать в
репозиторий или промпты. Они должны оставаться в Supabase Secrets либо в
локальном защищённом окружении Apollo1.

## 2. Что прочитать перед изменениями

Обязательно полностью прочитать:

1. `README.md` — состав проекта и подключение frontend-модулей.
2. `ARCHITECTURE.md` — действующая архитектура Tilda + GitHub + Supabase.
3. `DATABASE.md` и `SCHEMA.md` — база данных и назначение таблиц.
4. `FUNCTIONS.md` — Edge Functions, RPC и ночной pipeline.
5. `GIFT_QUIZ.md` — объединённый подбор подарков.
6. `CHANGELOG.md` — последние исправления и ограничения.
7. `imports/README.md` — импорт семантики.

Нельзя придумывать новую архитектуру, если задача решается существующими
таблицами, RPC, Edge Functions и frontend-модулями.

## 3. Ключевая архитектура

- Tilda отображает страницы, карточки, статьи и корзину.
- На сайт один раз подключён `sweetgift-loader.js`.
- `sweetgift-manifest.json` определяет, какие JS-модули загружать на странице.
- После изменения frontend-модуля необходимо увеличить его `version` в
  manifest, иначе jsDelivr и браузеры могут оставить старый файл в кеше.
- Supabase хранит каталог, составы, статьи, SEO-сущности, рекомендации,
  аналитику и состояние pipeline.
- Тяжёлые товарные подборки рассчитываются заранее; frontend должен получать
  готовые данные, а не выполнять тяжёлые расчёты при открытии страницы.
- Подборки статей дополнительно публикуются как статические JSON-файлы в
  `article-products-cache/` и обновляются workflow
  `.github/workflows/article-products-cache.yml`.
- Публичный CDN использует файлы GitHub через jsDelivr.
- Алкогольные разделы централизованно исключены из публичных подборок.

## 4. Работа с Git

Перед каждым изменением:

```bash
git status --short
git pull --ff-only origin main
```

Не перезаписывать чужие незавершённые изменения. Не использовать
`git reset --hard`, `git checkout --` и принудительный push без отдельного
подтверждения владельца проекта.

После изменений выполнить подходящие проверки, показать `git diff`, затем:

```bash
git add -- <изменённые-файлы>
git commit -m "Краткое описание изменения"
git push origin main
```

## 5. Проверки

Для изменённого JavaScript:

```bash
node --check path/to/file.js
```

Для manifest:

```bash
node -e "JSON.parse(require('fs').readFileSync('sweetgift-manifest.json','utf8'))"
```

Для всего изменения:

```bash
git diff --check
git status --short
```

Для статьи или пользовательского сценария после push проверить опубликованную
страницу SweetGift с параметром, исключающим старый кеш, и убедиться, что
загружена новая версия модуля.

## 6. Supabase и миграции

- Перед изменением схемы сверить список применённых миграций в Supabase с
  `supabase/migrations/`.
- Не применять повторно миграцию, которая уже есть в истории проекта.
- DDL оформлять миграцией и применять через официальный Supabase MCP/CLI.
- После изменения функции проверить её реальным SQL/RPC-вызовом.
- Для функций с `security definer` обязательно проверять `search_path`, права
  `EXECUTE` и невозможность доступа к закрытым данным.
- Не менять RLS, серверную авторизацию или структуру данных без проверки
  безопасности и явного понимания влияния на frontend.

## 7. Деплой Edge Functions

Исходники находятся в `supabase/functions/`. При изменении функции необходимо:

1. проверить код и зависимости;
2. развернуть именно изменённую Edge Function в проект
   `rvgvbxipccbkytmhltmi`;
3. проверить логи и реальный HTTP/RPC-сценарий;
4. зафиксировать тот же исходник в GitHub.

Секреты функций не должны попадать в исходный код.

## 8. Ночной pipeline

Сохранять существующую последовательность:

1. импорт каталога;
2. импорт индекса статей;
3. классификация статей и сущностей;
4. пересчёт товарных подборок;
5. обновление статического кеша;
6. ежедневный отчёт.

При сбое сначала смотреть `pipeline_runs`, журналы Edge Functions и фактическую
сверку источников. Не запускать несколько тяжёлых пересчётов параллельно.

## 9. Что считать источником истины

- код, миграции и документация — `origin/main`;
- рабочие данные и история применённых миграций — Supabase-проект
  `rvgvbxipccbkytmhltmi`;
- страницы, товары и статьи — опубликованный сайт Tilda;
- секреты — Supabase Secrets/защищённое окружение, но не GitHub.

Если GitHub и Supabase расходятся, сначала провести read-only сверку и описать
расхождение. Не исправлять историю миграций догадками.

На момент передачи история рабочей базы включает
`20260901100120_neuromaria_product_details_v1`; соответствующий SQL восстановлен
в GitHub из фактического определения функции. В рабочей базе его повторно не
применять.
