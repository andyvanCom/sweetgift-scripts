# SweetGift Architecture

Актуально на 2026-09-02.

## Назначение

SweetGift — технологический слой поверх Tilda. Tilda остаётся системой публикации страниц, каталога, статей и оформления заказа. GitHub хранит версионируемый код и статический кеш. Supabase выполняет импорт, хранение, аналитику, рекомендации и фоновые задачи.

```text
Tilda / sweetgift.ru
        │
        ▼
sweetgift-loader.js → sweetgift-manifest.json → frontend-модули
        │                                      │
        ├──────── jsDelivr / GitHub cache ─────┤
        │                                      ▼
        └────────────────────────────── Supabase Data API / Edge Functions
                                               │
                                               ▼
                                     PostgreSQL + pg_cron + pg_net
```

## Источники истины

- страницы, товары, статьи и форма заказа: опубликованная Tilda;
- код, миграции и документация: `origin/main` GitHub;
- рабочие данные и история применённых миграций: Supabase `rvgvbxipccbkytmhltmi`;
- секреты: Supabase Secrets или защищённое окружение, никогда не GitHub.

## Frontend

На сайте подключается только `sweetgift-loader.js`. Loader читает manifest, определяет путь страницы, сначала загружает `core`, затем разрешённые модули. Повторная загрузка блокируется.

`sweetgift-core.js` предоставляет общие RPC/REST-запросы, таймауты, нормализацию URL, visitor ID, экранирование и загрузку Supabase client. Публичный frontend использует только publishable/anon-доступ и разрешённые RPC. Service role в браузере запрещён.

Manifest на 2026-09-02 содержит 17 записей. Активны:

- общие: core, share, product analytics, order tracker, badges, live popup, recent products, top widgets, product SEO blocks, gift quiz;
- статьи: article stats, article products, copy source;
- рейтинги: top pages и top articles;
- страницы подбора: gift selector.

`product-top-lists` сохранён, но отключён.

### Статьи и товарные подборки

Статья содержит один или несколько контейнеров:

```html
<div class="sg-related-products" data-mode="auto" data-alias="article-alias"></div>
```

Основной Alias берётся из `data-alias`; URL используется только как fallback для старых публикаций. Каждый контейнер независим. Одинаковые Alias разделяют запрос. MutationObserver обрабатывает динамическую отрисовку Tilda.

Порядок получения данных:

1. статический JSON из `article-products-cache/` через jsDelivr;
2. Edge Function `article-products`;
3. прямой read-only RPC `get_article_products` как резерв.

Блок «Читайте также» использует реальные заголовки `articles_index`, удаляет повторные анкоры, визуально показывает 8 ссылок на desktop и 5 на mobile, но оставляет все ссылки в DOM.

### Карточка товара

`sweetgift-product-seo-blocks.js` получает готовый `product_card_seo_blocks` через `get_product_card_seo_blocks_cached`. Пользователь видит четыре независимых блока: «Вы уже смотрели», «Входит в списки», «Советы и статьи», «Похожие композиции».

Похожие композиции заранее учитывают пересечение ингредиентов, близость цены, категорию и популярность. Алкогольные специализированные разделы исключаются серверными защитами.

### Подбор по составу

`sweetgift-gift-selector.js` обслуживает:

- `/podbor-po-sostavu` — подарочные корзины;
- `/podbor-naborov-po-sostavu` — подарочные наборы и боксы.

Каталог запрашивается один раз, затем AND-фильтрация ингредиентов выполняется в браузере. Выбор отражается в URL и может быть отправлен через системный шаринг. При нулевом результате форма отправляет запрос через Edge Function `gift-selector-request`.

### Единый квиз

`sweetgift-gift-quiz.js` разделяет пользователя на три ветки: корзина, бокс или клубника в шоколаде. Результаты появляются после первого выбора и уточняются после каждого ответа. Backend — `get_gift_quiz_recommendations`; события — `track_gift_quiz_event`.

## Backend

Supabase используется для:

- каталога и вариантов товаров;
- структурированного состава;
- индекса и статистики статей;
- семантики и SEO-сущностей;
- товарных и статейных рекомендаций;
- рейтингов и агрегатов;
- обезличенной аналитики заказов и поведения;
- состояния pipeline и административных метрик.

Публичные операции оформлены ограниченными RPC. Таблицы public имеют RLS. SECURITY DEFINER допускается только с фиксированным `search_path`, ограниченными параметрами, явными правами и отсутствием выдачи закрытых данных.

## Предварительные расчёты

Ресурсоёмкие операции не выполняются при открытии страницы:

- `article_product_cache` готовится ночью;
- `product_card_seo_blocks` пересчитывается пакетно;
- `article_product_recommendations` готовится заранее;
- `top_lists` обновляется почасово;
- старые подробные события сворачиваются/удаляются по политике хранения.

Это снижает задержку frontend и сохраняет работоспособность при временной деградации Edge Functions.

## Импорт и классификация

```text
YML/CSV/Tilda → Edge import → normalized tables → classification
             → recommendations/cache → static JSON → frontend
```

- `import-yml-products` обновляет каталог, состав и варианты;
- `import-articles-index` синхронизирует опубликованные статьи и Alias;
- `classify-articles` назначает темы и сущности пакетами;
- кластерные `sync_*_article_filters` поддерживают правила article_product_filters;
- `refresh_article_product_cache` материализует выдачу для статей.

## Ночной цикл

Расписание Supabase задаётся в UTC:

| UTC | Задача |
|---|---|
| 04:00 | импорт YML товаров |
| 04:30 | импорт индекса статей |
| 04:45 | классификация статей |
| 05:00 | кеш товарных подборок статей |
| 05:15 | SEO-блоки карточек |
| 05:30 | рекомендации статей для товаров |
| 05:35 | архив подробных событий старше 180 дней |
| 05:45 | ежедневный отчёт |
| 05:50 | снимок метрик админки |

Отдельно рейтинги пересчитываются на 5-й минуте каждого часа. GitHub Actions экспортирует статический кеш в 05:30 UTC; при изменении расписания необходимо сохранять достаточный интервал после серверного пересчёта.

## Данные и приватность

Аналитика заказов хранит товарные позиции, суммы, промокод, скидку, доставку и обезличенные признаки. Имя, телефон, email, адрес и текст открытки не должны попадать в аналитические таблицы. Подробные product events хранятся 180 дней; агрегаты могут храниться дольше. Административные дневные снимки сохраняются 90 дней.

## Деплой

- frontend: изменить JS, увеличить version в manifest, проверить, commit/push;
- статический кеш: GitHub Action или `scripts/export-article-products-cache.py`;
- Edge Function: развернуть функцию и зафиксировать идентичный исходник в GitHub;
- PostgreSQL: добавить миграцию, сверить историю, применить один раз, проверить RPC и advisors;
- документация: обновить вместе со значительным изменением.

Принудительный push, повторное применение миграций и хранение секретов в репозитории запрещены.
